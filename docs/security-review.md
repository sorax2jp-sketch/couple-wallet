# Ver.1 Security Rules 最終監査

対象：Spark構成の `firestore.rules`、`src/wallet.ts`、`tests/rules.test.ts`。本番プロジェクトへの接続・設定・公開は行っていない。結果はローカルFirestore Emulatorにおけるルール評価に基づく。

## 結論と境界

要求されたクライアントからの不正アクセス・不整合な更新を拒否する構造を確認した。未精算明細の正当な金額・支払者の修正は許可し、集計の同時補正を必須にする。支出の実在、送金の完了、正当なメンバーの故意の虚偽入力は検証しない。

| 要件                           | Rules上の強制                                                                                          | 直接書き込みテスト                                                                                                         |
| ------------------------------ | ------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------- |
| 未ログインのアクセス拒否       | 全read/writeは認証・所属が必要。usersは自分のgetのみ。その他は既定拒否                                 | 6種のパスのget/create/update/delete、保護コレクションのlist、正しい形のatomic editを拒否                                   |
| 他householdの閲覧・更新拒否    | 対象householdのmemberUidsにrequest.auth.uidが含まれる必要あり                                          | 他家計に正規所属するユーザーのlist・更新、および完全に整合した不正編集batchを拒否                                          |
| memberUids不変                 | 許可する各mutationのaffectedKeysにmemberUidsを含めない。create/deleteも不可                            | 正当なrenameと組み合わせても差替・追加・削除・並替・重複を拒否。users対応表の変更も拒否                                    |
| 精算済み編集・削除不可         | 変更前後のcycleがcurrent、変更前deletedがfalse。物理deleteは許可なし                                   | 直接編集・削除、current cycleへ移すbatch、論理削除を拒否。精算レコードの更新・削除も拒否                                   |
| 金額・支払者による集計破壊拒否 | 型/範囲/所属検証とgetAfterを使い、両人のafter合計=before合計+新寄与−旧寄与を照合                       | 不正整数・外部支払者・片側だけ補正・余分な合計キー・負残高・明細単独・合計単独・複数明細の混入を拒否。正当修正の成功も確認 |
| 精算cycle/合計の原子性         | 当該cycleの新規精算記録と家計revision+1/次cycle/両合計0を必須化。差額/方向/スナップショット/時刻も照合 | 各項目を単独で改ざん、記録なしリセット、cycle再利用、隠れた明細の同時追加を拒否。追加対精算、精算対精算の競合も確認        |

初期登録の重複UIDは監査時に防御を追加し、更新をfail closedにした。Console管理者が正しく異なる2人のUIDとmapキーを初期登録することが前提。Rulesは任意の管理者書き込みを修復するものではない。

## 実行方法と結果

```sh
npm run test:rules
npm test
npm run build
npm run format:check
git diff --check
```

開発用の `npm run emulators` が起動中なら先に停止する（同じ8080ポートを使う）。自動テストは独立したdemoプロジェクトで起動し、本番データを使わない。Rulesテストは `execute()` のクライアント側チェックに頼るケースだけでなく、Web SDKから直接batch/update/deleteを送る攻撃を含む。拒否されたbatchに部分更新が残らないことも確認する。負のテストに出るPERMISSION_DENIEDログは期待結果であり、全テスト成功かどうかはrunnerの結果で判定する。

Rulesテスト27件、計算/画面20件とApp Check設定4件の計24件を実行し、すべて成功した。テスト数は攻撃試行の数ではなくrunner上のケース数であり、各ケース内に複数の不正入力を含む。有限のテストが全ての攻撃を網羅する保証ではない。

## 秘密情報と導入

`.env.example` は公開Web設定の空値とfalseのみ。`.env*`、`.vercel/`、秘密鍵、典型的サービスアカウントJSON名をignoreし、例ファイルのみ共有可能にする。秘密鍵/サービスアカウント形式の限定スキャンでは対象アプリ・設定・テストから該当なし。任意の秘密文字列やGit履歴全体の漏えいが不存在であることを証明するスキャンではない。

本番導入はREADMEのクリック手順に従う。Rulesを正しくPublishし、App CheckのFirestore enforcementを有効にして初めて本番の防御が揃う。複合indexは不要でcycleIdの既定単一フィールドindexが必要。Authの独立した任意のsignupを完全に禁止する構成ではないが、未登録のUIDには家計アクセスを一切許可しない。

公開後の実機チェックは未実施。Console/IAM権限はRulesを迂回できる。認証情報の漏えい、端末乗っ取り、管理者の誤操作、無料枠枯渇、履歴保全は運用責任として残る。App Checkは人の本人確認や悪意ある正規メンバーの抑止を代替しない。

## Enterpriseプロバイダーへの変更

App Checkを `ReCaptchaEnterpriseProvider` と公開 `VITE_RECAPTCHA_ENTERPRISE_SITE_KEY` へ変更。旧v3キーでは設定完了と扱わない。本番でのEnterprise選択・自動更新、Emulator時だけの省略、本番でEmulatorフラグを立てても省略されないことをモック境界の4テストで確認する。実際のEnterprise評価・トークン・本番の強制適用や最新料金表を検証するテストではない。無料枠と確認できていない公式情報はREADMEで明記している。Rulesの認可・集計整合性は変更していない。
